PHASE 0 — Pre-test checklist
Before starting any test, confirm the following physically:

#	Item	Status
0.1	KrakenSDR powered and USB cable connected to Raspberry Pi	
0.2	CH0 and CH1 SMA ports connected to Iridium (1621 MHz) antennas via LNA	
0.3	CH2 and CH3 SMA ports connected to Inmarsat (1641 MHz) antennas via LNA	
0.4	LNAs have bias-tee power (or external DC, depending on your setup)	
0.5	Iridium buoy powered on and has a GPS fix	
0.6	Inmarsat buoy powered on and has a GPS fix	
0.7	Raspberry Pi on the same local network as your laptop for SSH access	
0.8	Google Drive rclone remote configured (rclone listremotes shows gdrive:)	

# Quick rclone check
rclone listremotes
Expected: gdrive: appears in the output.

PHASE 1 — Hardware: KrakenSDR USB detection
Goal: Confirm the OS sees all 5 RTL-SDR devices before any software touches them.

T-01 — USB devices detected


lsusb | grep -i "RTL\|Realtek\|2838"
Expected: Exactly 5 lines, all showing the same chip (RTL2838 or similar).

Stop the DAQ daemon first if it is running, then run the receiver checker:


sudo systemctl stop daq_chain 2>/dev/null || true

Expected:


Todos los dispositivos detectados

  ✓ Dispositivo 1: OK
  ✓ Dispositivo 2: OK
  ✓ Dispositivo 3: OK
  ✓ Dispositivo 4: OK
✓ Todos los 5 RTL-SDRs del KrakenSDR están operativos!
If any device shows ERROR, reseat the USB cable, wait 10 seconds, and retry.

cd /home/kraken/Signal-Recorder

PHASE 3 — RF signal verification (no recorder, eyes-only)
Goal: Confirm you can actually receive signal at both frequencies with your antenna + LNA setup before trusting any automated detection. This is your RF sanity check.

T-04 — Iridium signal visible at 1621.3 MHz

Open a second terminal and run the pulse monitor on CH0:


source venv/bin/activate
python src/pulse_monitor.py --freq 1621.5 --samplerate 2.4 --device 0 --gain 49.6
Wait up to 30 minutes. Iridium NEXT satellites pass frequently; you should see bursts in the terminal well before the buoy transmits.

Expected: Lines like:


🔴 PULSO #1 DETECTADO!
   ├─ Potencia: -78.3 dB
   ├─ Delta: +8.4 dB sobre baseline
   └─ Timestamp: 14:23:07.412
   └─ Duración: 90.0 ms
Note: Even without your buoy transmitting, you will see general Iridium traffic from other sources. If you see nothing after 30 minutes, recheck LNA power and cable connections.

T-05 — Inmarsat signal visible at 1641.5 MHz


python src/pulse_monitor.py --freq 1641.5 --samplerate 2.4 --device 2 --gain 49.6
Inmarsat is a geostationary satellite — once you find the pointing direction the signal is continuous. You should see regular pulses or a constant elevated baseline within minutes.

Expected: Pulses detected or clearly elevated power above baseline on CH2.

T-08 — Inmarsat buoy transmission detected and saved

Same as T-07 but for the Inmarsat buoy. Place it near CH2/CH3 antennas if needed.

Expected: Same ⚡ line with [Inmarsat] and 2 .iq files for CH2 and CH3.

T-09 — 10-second cooldown enforced

If during T-07 or T-08 you see two events from the same group within 10 seconds, this test fails. Normal satellite burst traffic should not retrigger within the cooldown window.

To verify manually: confirm in the output that after an event, no new ⚡ [Iridium] or ⚡ [Inmarsat] line appears for at least 10 seconds.

Expected: Minimum 10 seconds between consecutive events from the same group.

T-10 — Both groups detect independently

This test passes automatically if T-07 and T-08 both pass during the same recording session — it confirms the two frequency groups (different SDR channels, different frequencies) operate independently.

PHASE 5 — File content verification
Goal: Confirm the saved .iq files contain valid, readable data with correct metadata and both the pre-event and post-event content.

T-11 — Header metadata is correct

Run this on one of the files saved in T-07:


python3 - <<'EOF'
import struct, json, sys
path = sorted(__import__('glob').glob('/home/kraken/Signal-Recorder/events/event_Iridium_*.iq'))[0]
with open(path, 'rb') as f:
    hlen = struct.unpack('I', f.read(4))[0]
    h = json.loads(f.read(hlen))
    f.read(8)  # timestamp
    n = struct.unpack('I', f.read(4))[0]

print(f"File:          {path}")
print(f"Group:         {h['group_name']}")
print(f"Center freq:   {h['center_freq']/1e6:.4f} MHz")
print(f"Target freq:   {h['target_freq']/1e6:.4f} MHz")
print(f"Sample rate:   {h['sample_rate']/1e6:.2f} MHz")
print(f"Gain:          {h['gain']} dB")
print(f"Pre samples:   {h['pre_samples']:,}  ({h['pre_samples']/h['sample_rate']:.2f} s)")
print(f"Post samples:  {h['post_samples']:,}  ({h['post_samples']/h['sample_rate']:.2f} s)")
print(f"Peak power:    {h['peak_power_db']:.1f} dB")
print(f"Baseline:      {h['baseline_power_db']:.1f} dB")
print(f"Total samples: {n:,}")
EOF
Expected:

Center freq = 1621.3000 MHz
Target freq = 1621.3000 MHz
Sample rate = 1.50 MHz
Gain = 40.0 dB
Pre samples ≈ 4,500,000 (≈ 3.0 s) — may be slightly less if recorder started recently
Post samples ≈ 4,500,000 (≈ 3.0 s)
Peak power noticeably above Baseline (difference > threshold_db)
T-12 — IQ data is non-zero and finite


python3 - <<'EOF'
import struct, json, numpy as np, glob
path = sorted(glob.glob('/home/kraken/Signal-Recorder/events/event_Iridium_*.iq'))[0]
with open(path, 'rb') as f:
    hlen = struct.unpack('I', f.read(4))[0]
    f.read(hlen); f.read(8)
    n = struct.unpack('I', f.read(4))[0]
    raw = np.frombuffer(f.read(n * 2 * 4), dtype=np.float32)

samples = raw[0::2] + 1j * raw[1::2]
print(f"Total samples:  {len(samples):,}")
print(f"All finite:     {np.all(np.isfinite(samples))}")
print(f"Non-zero:       {np.any(samples != 0)}")
print(f"RMS amplitude:  {np.sqrt(np.mean(np.abs(samples)**2)):.6f}")
print(f"Peak amplitude: {np.max(np.abs(samples)):.6f}")
EOF
Expected:

All finite: True
Non-zero: True
RMS amplitude > 0 (typically 0.001 – 0.3 depending on gain and signal strength)

PHASE 6 — Systemd service
Goal: Confirm the recorder starts automatically at boot and self-heals after failures.

First install the service if not yet done:


sudo cp /home/kraken/Signal-Recorder/signal-recorder.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now signal-recorder
T-14 — Service is active immediately after install


systemctl status signal-recorder
Expected: Active: active (running) and the calibration output visible in recent journal lines:


journalctl -u signal-recorder -n 20
T-15 — Service survives a process kill


# Kill the recorder process (simulates a crash)
sudo kill -9 $(pgrep -f "python main.py")

# Wait 35 seconds (RestartSec=30 + margin)
sleep 35

systemctl status signal-recorder
Expected: Active: active (running). The service has restarted automatically. The journal shows:


signal-recorder[XXXX]: Process killed (signal 9)
signal-recorder[YYYY]: Calibrating noise floor...
T-16 — Service survives a reboot


sudo reboot
After reboot, SSH back in and immediately check:


systemctl status signal-recorder
Expected: Active: active (running) without any manual intervention.

T-17 — Heartbeat logs service state

After the service has been running for at least an hour, check status.log:


tail /home/kraken/Signal-Recorder/status.log
Expected: Lines like:


[2026-05-09 15:00:00] Red: OK | Servicio: active | Archivos pendientes: 4
The Servicio field must show active, not failed or unknown.

Common failure modes and fixes
Symptom	Likely cause	Fix
T-02 fails on one device	USB contention or loose SMA	Reseat USB cable; run sudo udevadm settle
T-06 shows "not yet ready"	daq_chain still holding USB	sudo systemctl stop daq_chain
T-07 never fires despite buoy transmitting	Threshold too high for your noise floor	Lower threshold_db from 12 to 8 in main.py
T-07 fires constantly (false positives)	Wideband interference on boat	Raise threshold_db to 15–18, or narrow detection_bw_hz to 50e3
T-15 service doesn't come back	StartLimitIntervalSec hit (shouldn't happen)	sudo systemctl reset-failed signal-recorder && sudo systemctl start signal-recorder
T-18 files not deleted	rclone remote not configured or wrong name	rclone config — confirm remote is named exactly gdrive
